### Per-file Details (expanded)

This section gives a short 3–4 line description for every file and folder in the repository (excluding `node_modules`). Use it as an authoritative guide for the purpose, risks, and maintenance notes for each item.

Root files

- `.git/` — Git metadata directory (branches, refs, hooks). Not part of the application; contains useful hooks and should not be modified by day-to-day development. Keep pre-commit hooks minimal and non-blocking for faster local workflows.

- `.vscode/` — Editor-specific workspace settings and recommended extensions. Useful for sharing launch tasks, debugging settings and editor configs among the team; avoid storing secrets here.

- `DEPLOYMENT.md` — Step-by-step production deployment instructions, including environment requirements, TLS/NGINX setup and migration workflow. Update this on every deployment change and include rollback steps for safe releases.

- `README.md` — Project overview, quickstart, and links to docs. Keep the README succinct; point to `DEPLOYMENT.md`, `PROJECT_STRUCTURE.md` and testing/development guides.

- `PROJECT_STRUCTURE.md` — This file. The canonical reference for repository layout and file purposes. Keep it synced with major structural changes and add cross-links to deeper docs.

- `SECURITY_EVALUATION.txt` — Notes and findings from a security review. Archive remediation steps and link to tickets for each finding; treat it as living documentation for security hygiene.

- `SECURITY_WORKFLOW_EXPLAINED.md` — Explains attacker models, incident response playbooks and the workflow for triage and remediation. Keep up-to-date to shorten mean-time-to-remediation.

- `backup.sh` — Backup automation script for DB snapshots; compresses and optionally uploads dumps. Ensure it runs under least-privileged accounts and uses secrets from the environment.

- `monitor.sh` — Healthcheck script for uptime and quick operational checks. Integrates with alerts; define thresholds appropriately for production versus development.

- `docker-compose.yml` — Local and staging compose orchestration for services (frontend, backend, DB, nginx). Good for reproducible dev environment; do not use the same compose file as production without validating resource constraints.

- `nginx.conf` — Reverse proxy configuration used in containerized or VM deployments. Contains routes for TLS termination, rate-limiting and security headers; ensure the file is audited for header and SSL best practices.

Backend (`OnlineFirPortal.backend`)

- `.env` — Example environment variables to configure the application. Document required variables (`DATABASE_URL`, `JWT_SECRET`, `ENCRYPTION_KEY`) and recommended formats; never put real secrets here.

- `.env` — Local environment override (gitignored). Used for running local server and tests; handle with care and don't commit.

- `Dockerfile` — Builds the backend container image; references runtime Node/TSC build steps. Keep it lean and secure (use non-root user when possible and multi-stage builds for smaller images).

- `bun.lock` — Lockfile for bun environments. Use alongside `package-lock.json` if bun is used for local development.

- `package.json` — Backend npm manifest: dependencies, scripts and Jest config. Update scripts and ensure test/coverage scripts are safe in CI.

- `tsconfig.json` — TypeScript build and checking configuration. Coordinated with `ts-jest` and ESLint; changing compiler flags may break builds.

- `coverage/` — Generated coverage artifacts (LCOV/html/json). `lcov-report/` is viewable locally; CI may upload `coverage-final.json` to coverage tooling.

- `data/firs.test.db` — SQLite file used for test runs. Tests set up and tear down data; don't assume persistence between runs unless intentionally archived.

- `data/ipc.json` — Local test/config data used by IPC helper endpoints and tests; useful for injecting test artifacts.

- `dist/` — Output from production build (if server is compiled out-of-line). Not checked into source; can be used for Docker production images.

Prisma folder

- `prisma/schema.prisma` — Source of truth for data models and enums used by Prisma. Changing models requires migrations and careful deploy planning for production.

- `prisma/migrations/...` — Migration folders created by Prisma for schema updates. Each folder contains SQL or steps used to apply schema changes incrementally; keep these committed.

- `prisma/migration_lock.toml` — Lockfile to coordinate migration states across environments; helps avoid concurrent migration runs.

- `prisma/dev.db` — An optional local SQLite used for dev convenience; do not rely on it in CI.

Backend source (`src/`)

- `src/server.ts` — Express application entry point that wires middleware, routes and security configuration. Contains the `if (require.main === module)` server bootstrap; prefer not to import side-effectful bootstraps in tests.

- `src/scripts/generate-keys.ts` — Utility script to locally generate RSA key pairs for digital signatures in dev. Keep private keys offline; use the output to test signature flows.

src/lib (per-file)

- `src/lib/access-control.ts` — Central RBAC implementation: role definitions, permissions matrix and helper functions such as `hasPermission` and `canAccessFIR`. Test authorization logic comprehensively as it enforces data isolation.

- `src/lib/audit-logger.ts` — Writes audit events to DB and standardizes change payloads. Used to create tamper-evident trails required for compliance and incident investigations.

- `src/lib/auth-middleware.ts` — Token extraction and verification middleware, MFA checks and `requireRole` helper. This is critical for security; any changes must be covered by integration tests.

- `src/lib/database-connection.ts` — Optional helpers for database connectivity and graceful shutdown. Useful in worker processes or background jobs to manage DB lifecycles robustly.

- `src/lib/db.ts` — Lightweight helpers for raw queries used in tests and setup scripts. Not intended for application business logic; useful for cleanup and fixtures.

- `src/lib/jwt.ts` — Handles access/refresh token generation, verification, and helper payload types. Uses environment secrets and safe defaults for expiry, issuer and audience.

- `src/lib/notification-service.ts` — Abstracts notification channels (SMS, Email, In-App). Adapters allow swapping providers (e.g., Twilio/SendGrid) while keeping application code unchanged.

- `src/lib/password-service.ts` — Implements password policy validation, password history enforcement, reset token lifecycle and admin approvals. Security-critical: ensure token hashing and expiry rules are robust and tested.

- `src/lib/prisma.ts` — Creates the singleton Prisma Client, ensures migrations are applied during test runs and contains bunx/npx fallbacks. Prevent multiple clients to avoid connection pool exhaustion.

- `src/lib/security-middleware.ts` — Helmet, HPP, rate limiters and sanitizers applied globally to incoming requests. It's the first line of defense for input sanitation and header-based security protections.

- `src/lib/security.ts` — Cryptographic primitives and helpers: AES-GCM encryption/decryption, RSA key/sign/verify, base64 helpers and helper functions for FIR number generation. Strongly unit-test these utilities and ensure `ENCRYPTION_KEY` is enforced in production.

- `src/lib/session-service.ts` — Session management helpers (create, revoke, expire). Sessions provide server-side control over device-level access and are useful for audit and session revocation features.

- `src/lib/totp-service.ts` — TOTP secret and QR generation and verification using Speakeasy and QR code DataURL generation. Generates recovery codes and handles clock-drift tolerances.

src/routes (per-file)

- `src/routes/auth.ts` — Implements register/login/TOTP/verify-recovery-code/register-public-key/logout/refresh endpoints. Handles password validation, account lockouts, MFA flows and session creation.

- `src/routes/firs.ts` — Endpoints for FIR creation, submission (with optional signature verification), assignment, status updates, notes and stats. Uses encryption helpers and timeline/audit log creation for traceability.

- `src/routes/admin.ts` — Admin-only endpoints for user management, password resets approval, viewing audit logs and generating administrative reports; heavily audited and access-restricted.

- `src/routes/documents.ts` — File upload/download endpoints with validation, encryption for stored content, and verification workflow for evidence files.

- `src/routes/ipc.ts` — Internal/testing helpers used by integration tests or local tooling to inject OTPs or mock internal events; should be restricted or removed in production.

Tests

- `test/` — Unit and library tests that exercise utilities and small components in isolation (fast, deterministic tests).
- `tests/` — Integration tests using `supertest` against the running Express app; these rely on the disposable SQLite DB and are the authoritative check for API behavior.

Frontend

- `OnlineFirPortal.frontend/package.json` — Frontend npm manifest and scripts (`dev`, `build`, `test`). Keep dev and CI scripts aligned to avoid environment drift.

- `OnlineFirPortal.frontend/next.config.mjs` — Next.js runtime config including API rewrites to proxy to the backend during development. Keep experimental settings to a minimum and ensure settings are compatible with the host platform.

- `OnlineFirPortal.frontend/vitest.config.ts` & `vitest.setup.ts` — Unit test configuration and setup (JSDOM, global mocks like `localStorage` polyfill used in tests).

- `OnlineFirPortal.frontend/playwright.config.ts` — Playwright configuration for E2E tests (browsers, timeouts, baseUrl). E2E tests should run in dedicated CI stages with stable test instances.

- `OnlineFirPortal.frontend/app/` — Next.js application routes and pages. Each folder under `app/` contains page code and may include nested layouts and modularized components.

- `OnlineFirPortal.frontend/components/` — Shared components used across pages (UI primitives, layout elements, app-specific widgets like `evidence-upload` and `notification-bell`).

- `OnlineFirPortal.frontend/lib/` — Client libraries including `auth-store.ts` (auth state), `digital-signature.ts` (client RSA helpers), `fir-store.ts` (data access) and `use-auto-save.ts`.

- `OnlineFirPortal.frontend/public/` — Static assets served by Next: PWA manifest, placeholders, SW script and icons. Keep asset sizes reasonable and optimize images for web.

- `OnlineFirPortal.frontend/tests/` — Unit and E2E tests: `auth-store.test.ts`, `digital-signature.test.ts`, and Playwright specs. Keep mocks stable and E2E tests isolated to dedicated test environments.

## 🔧 Backend (`OnlineFirPortal.backend/`)

### Root Files

`OnlineFirPortal.backend/`

- `package.json` — Project manifest and npm scripts.
  - Lists production and dev dependencies and configures scripts used in development and CI (test, build, dev). Keep this up-to-date when adding libraries or commands.
  - Security note: ensure secrets are not stored here; use `.env` for runtime secrets and CI environment variables for pipelines.
  - Typical operations: `npm install`, `npm test`, `npm run build` and script hooks used by CI/CD.

- `tsconfig.json` — TypeScript compiler options and path mapping.
  - Sets strictness flags, target and module resolution, and rootDirs used by the build step.
  - Changing `tsconfig` can affect type checking and emitted JavaScript; keep it aligned with `eslint` and `ts-jest` settings.
  - Used by IDEs and tooling (editor intellisense, tsc, ts-node).

- `.env` — Templated environment variables for new developers and deployment manifests.
  - Documents required runtime variables such as `DATABASE_URL`, `JWT_SECRET`, `ENCRYPTION_KEY` and how to format them.
  - Should be safe to commit; never include real secrets here.
  - Use this as a reference to create a local `.env` (gitignored) for development.

- `.env` — Local environment overrides (git-ignored).
  - Contains secrets for local development (database path, test keys). Treat with strict secrecy and do not commit.
  - The backend code reads these variables at startup (unless running in test mode where a test DB path can be injected).
  - In production, prefer proper secret stores instead of raw `.env` files.

- `prisma/` — Database schema, migrations and sample DBs.
  - `schema.prisma` defines the database models, relations and enums used by Prisma.
  - `migrations/` contains migration steps that are applied during deploy or test startup.
  - There may be sample DBs (`dev.db`) and migration lock files to reproduce local environments.



**Purpose:**
- `package.json` - Defines backend dependencies (Express, Prisma, JWT, etc.)
- `tsconfig.json` - TypeScript compiler settings
- `.env` - Database URL, JWT secrets, encryption keys

**Detailed File Descriptions:**

#### **`access-control.ts`**
- Implements the role-based access matrix used across the app. Exports helpers to check if a role (CITIZEN, OFFICER, ADMIN, etc.) may perform a specific action on a resource and contains helper functions like `canAccessFIR`.
- Centralizes authorization logic so route handlers can rely on consistent checks and audit logging when access is denied.
- Keep this file small and declarative — business rules should live here and be covered by unit tests.

#### **`audit-logger.ts`**
- Provides typed helpers to persist audit events to the `AuditLog` table. It formats and sanitizes `changes` and attaches metadata (user, IP, action) before writing.
- Used throughout auth, FIR, and admin flows to create a tamper-evident trail required for compliance and post-incident investigation.
- Includes helpers for authentication attempts, FIR ops, and user management operations; errors are logged but do not block main flows.

#### **`auth-middleware.ts`**
- Express middleware that extracts JWT tokens from Authorization headers or cookies and verifies them using `jwt.ts` utilities.
- Asserts MFA verification, attaches a lightweight `req.user` payload for downstream handlers, and provides `requireRole` helper middleware.
- All protected routes import these middleware functions; treat changes here carefully to avoid breaking access checks.

#### **`database-connection.ts`**
- Small helper utilities around database connection health checks and optional connection bootstrapping for long-running jobs or workers.
- Useful abstractions for connection retries and graceful shutdown handling in production environments.
- Keeps lifecycle management (connect / disconnect) out of route code.

#### **`db.ts`**
- Lightweight convenience wrapper(s) used by tests and quick scripts to run raw queries or to get direct DB access without Prisma models.
- Not intended for core application logic (use Prisma client for type-safe DB access), but useful for test setup/teardown and migrations.
- Additive utility functions here speed up test scaffolding and debugging.

#### **`jwt.ts`**
- Encapsulates token creation and verification logic (access and refresh tokens) and token expiry policies.
- Uses environment secrets (`JWT_SECRET`, `JWT_REFRESH_SECRET`) with secure signing options (issuer, audience). Also contains small helpers to create temporary tokens for flows like MFA setup.
- Includes safe fallbacks for randomness and logs warnings when secrets are missing.

#### **`notification-service.ts`**
- Abstracts sending notifications via email, SMS and in-app channels.
- Currently has mock implementations for development; adapters are designed so you can plug in Twilio, SendGrid, or other providers.
- Relevant for audit workflows that require user notifications (FIR updates, account lockouts, OTPs).

#### **`password-service.ts`**
- Implements password strength validation, password history checks, reset token generation and persistence, and reset approval logic for privileged flows.
- Encapsulates token hashing and expiration details and exposes helper functions used by the `/auth` routes and admin flows.
- Enforces policies such as minimum length, complexity and forbids reuse via the `passwordHistory` field.

#### **`prisma.ts`**
- Creates a single shared Prisma client instance for the process and contains the small test-time migration bootstrapper (deploys migrations in test env to ensure schema is up-to-date).
- Includes fallbacks for environments without `bunx` so `npx prisma migrate deploy` runs when necessary.
- Avoid creating multiple Prisma clients per module to prevent DB connection exhaustion and leaking file descriptors.

#### **`security-middleware.ts`**
- Express middleware for sanitizing incoming request bodies / queries and adding general security headers with `helmet` and `hpp`.
- Includes a defensive sanitizer that cleans strings of potentially dangerous tags and attributes; executed early in the middleware chain.
- Keep logic minimal here because schema validation (Zod) is the canonical source of validation for each endpoint.

#### **`security.ts`**
- Core cryptographic utilities: AES-GCM encryption/decryption helpers, RSA key generation, signing and verifying, base64 helpers, and helper functions for token generation.
- Enforces use of `ENCRYPTION_KEY` (throws in production; warns in development) to prevent accidental usage of insecure defaults.
- Implement unit tests for these functions because cryptographic regressions are silent and destructive.

#### **`session-service.ts`**
- Manages server-side session records (`Session` model): creation, revocation, expiry, and simple session lookup used during refresh and logout flows.
- Sessions are useful for auditability and for implementing per-device logout/session revocation.
- Includes TTL handling and cleanup hooks to avoid indefinite session growth.

#### **`totp-service.ts`**
- Wraps `speakeasy` + `qrcode` to provide TOTP secret generation (QR + manual key) and verification logic.

**Route Files Explained (detailed):**

#### **`auth.ts`**

#### **`documents.ts`**
- Manages evidence files associated with FIRs: secure upload, server-side or client-side encryption handling, metadata storage, and secure downloads.
- Uploads are validated for allowed types/size, stored encrypted, and indexed with metadata (uploader, FIR id, document type). There are endpoints for downloading and verifying integrity/verification status.

#### **`ipc.ts`**
- Small utility endpoints used for internal automation and test flows (for example, sending mock notifications, injecting OTPs in tests or administrative utilities).
- Not intended as a public API; protect or remove IPC endpoints in production builds or restrict them behind admin-only guards and environment flags.

### Database (`prisma/`)

```
prisma/
├── schema.prisma        # Database schema definition
└── migrations/          # Database migration history
```

#### **`schema.prisma`**
- **Purpose:** Central source of truth for data models and relationships used by Prisma and the application.
- **Usage:** Run `npx prisma generate` to refresh the client after changes, and `npx prisma migrate` to update the database schema. Keep model changes backward-compatible in production (use new migrations and careful deploys).

**Models (detailed):**
- `User` — Represents citizens, officers, and admins.
  - Contains authentication fields (password hash/salt), MFA state (secret, enabled, recovery codes), account security (failed login attempts, lockedUntil), and optional digital signature public key.
  - Indexed on email/mobile for fast lookups and provides relations to FIRs, sessions, audit logs, and documents.
  - Be careful with sensitive fields (mfa secrets, public keys) — treat them as protected attributes when returning API responses.

- `FIR` — First Information Report record.
  - Stores identification (reference number), reporter and assigned officer relations, incident metadata (date, place, type), and encrypted payloads for sensitive free-form descriptions.
  - Tracks lifecycle with `status`, `submittedAt`, `signedAt`, and `closedAt` and supports priority and assignment fields.
  - Includes indices on `reporterId`, `status` and `referenceNumber` to support efficient filtering in list APIs.

- `Document` — File attachments for FIRs.
  - Stores file metadata (filename, mimetype, size), encryption payload/reference and verification status.
  - Relates to FIR and uploader user; `encryptedContent` should be stored safely and streamed for downloads when required.
  - Consider virus scanning and content-type enforcement in upload flow.

- `AuditLog` — Security and activity audit trail.
  - Records who did what and when, with optional `changes` (JSON) describing before/after state; stores `ipAddress`, `userAgent` and other context for forensic work.
  - Append-only semantics are recommended: avoid deleting audit logs in normal operation.

- `Notification` — In-app/email/SMS notifications queued or sent to users.
  - Holds message and delivery metadata; track `sent`, `sentAt`, and `error` for retries and visibility.

- `Session` — Tracks active sessions and devices.
  - Useful for revoking access per device and showing active session lists to users; stores `refreshToken` metadata and last activity timestamps.

- `PasswordResetToken` & `MFARecoveryCode` — Security artifacts.
  - Reset tokens include expiration and optional admin approval fields for citizen flows; recovery codes are stored in hashed form and flagged when used.

**Key Fields & Security Notes:**
- Sensitive columns such as TOTP secrets and private keys must be protected and not returned to normal API consumers.
- Encrypted fields (e.g., `encryptedData`) should be encrypted with a server-side `ENCRYPTION_KEY` and not exposed raw in logs.
- Use migrations and test the migration plan before applying to production databases.

**Library Files Explained (detailed):**

#### **`auth-store.ts`**
- Central auth state manager used across components and layouts. It persists the minimal auth state to `localStorage`, exposes helpers to set MFA-required states, and provides login/logout helpers wired to API endpoints.
- Handles tempToken flows (for MFA), stores recovery codes temporarily during setup, and exposes a `useAuth` hook for components to reactively consume authentication state.
- Security considerations: avoid storing long-lived secrets or raw tokens if possible; prefer secure httpOnly cookies for access tokens when feasible.

#### **`fir-store.ts`**
- Client-side data access layer for FIR building and retrieval. Encapsulates fetch calls, client-side caching and optimistic updates for edits and status changes.
- Handles transformation of API payloads to UI-friendly shapes and performs front-end validations before calling the network.
- It is the single place to standardize error handling and retry behavior for FIR-related operations.

#### **`digital-signature.ts`**
- Implements RSA-PSS keypair creation using Web Crypto APIs (with a Node fallback for SSR tests), signing helpers and verification utilities used before sending or after receiving signed data.
- Keys are stored in `localStorage` (protected client-side) but may be exported/imported for user portability. The module abstracts key lifecycles and encourages secure handling (encourage passphrase protection in production-like setups).
- Tests validate cross-browser signing/verification consistency.

#### **`security.ts` (frontend)**
- Small helper utilities for base64 encoding/decoding, small cryptographic helpers used client-side (e.g., pre-hash before signing), and helpers to surface secure-generation of temp keys.
- Keep heavy crypto on the server; client-side crypto is useful for signatures and UX but should not be considered a substitute for server validation.

#### **`form-validation.ts`**
- Centralized validators used by forms (Aadhaar, mobile, emails and password strength). Exposes functions that return both boolean and human-friendly error messages.
- Works with Zod schema validation on the server side; keep UI validation focused on user experience and not as an authoritative gate.

#### **`use-auto-save.ts`**
- Debounces changes and persists drafts to `localStorage` with a last-saved timestamp and restore hook.
- Designed to be composable with form-state libraries and to avoid race conditions (writes are idempotent and lightweight JSON blobs).

#### **`utils.ts`**
- Misc utility helpers (date formatters, small UI helpers, random id generators). Keep it focused and well-tested to avoid accidental duplication across the codebase.

```

2. Auto-save to localStorage (use-auto-save.ts)
   ↓

   ↓

   ↓
8. Create audit log (audit-logger.ts)
   ↓
9. Send notification (notification-service.ts)
   ↓

```

   ↓

   ↓
4. Verify TOTP code
   ↓
5. Create user account (Prisma)
   ↓
6. Login with credentials
   ↓

## 🎯 Key Concepts

### Role-Based Access Control (RBAC)
- **Roles:** CITIZEN, OFFICER, SHO, ADMIN, SUPER_ADMIN
- **Implementation:** Middleware checks JWT role
- **Data Isolation:** Users only see their own data

### Digital Signatures
- **Algorithm:** RSA-PSS with SHA-256
- **Key Storage:** Client-side in localStorage
- **Public Key:** Registered with backend
- **Verification:** Backend verifies before accepting FIR

### Data Encryption
- **Algorithm:** AES-256-GCM
- **What's Encrypted:** FIR descriptions, evidence files
- **Key Management:** Server-side encryption key in .env

### Multi-Factor Authentication
- **Type:** TOTP (Time-based One-Time Password)
- **App:** Google Authenticator compatible
- **Backup:** 10 recovery codes generated
