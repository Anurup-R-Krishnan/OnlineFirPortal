# Contributing to OnlineFirPortal

Thank you for considering a contribution. This project demonstrates a civic
FIR filing system with evidence integrity, multi-factor authentication, audit
trails, and role-based police workflows. It is research and demonstration
software, and every contribution should keep that framing honest.

## Ground rules

- Keep claims verifiable. Do not add badges, coverage percentages, or
  readiness statements that the code does not support.
- Do not add AI attribution of any kind: no "Generated by", no co-author
  trailers, no AI tags in code, docs, or commit messages.
- Do not commit `.env` files, local databases, build output, or `node_modules`.
  Copy the `.env.example` files and keep real secrets out of the tree.
- Prefer small, focused changes that each solve one problem.

## Setting up for development

Backend (port 4001):

```bash
cd OnlineFirPortal.backend
npm ci
cp .env.example .env   # then fill in unique secret values
npx prisma generate
npm run dev
```

Frontend (port 4000):

```bash
cd OnlineFirPortal.frontend
npm ci
cp .env.example .env.local   # set API_BASE_URL=http://localhost:4001
npm run dev
```

## Running tests

Backend:

```bash
cd OnlineFirPortal.backend
npm run test:jest   # Jest unit + integration suite
npm run test:bun    # Bun end-to-end suite
```

Frontend:

```bash
cd OnlineFirPortal.frontend
npm test            # Vitest
```

Run the linter and type checks before opening a pull request:

```bash
cd OnlineFirPortal.backend && npx tsc --noEmit
cd OnlineFirPortal.frontend && npm run lint && npx tsc --noEmit
```

## Branch and pull request flow

1. Create a branch from `main` named after the change, for example
   `feat/evidence-hash` or `fix/login-lockout`.
2. Make your changes in small commits with conventional prefixes
   (`feat:`, `fix:`, `docs:`, `test:`, `chore:`, `refactor:`).
3. Open a pull request against `main`. Fill in the pull request template and
   confirm the checklist.
4. Ensure CI passes. The workflows run the backend test suite, frontend
   lint/type-check/test/build, and the Docker build.

## Commit conventions

- One logical change per commit.
- Conventional prefix in the subject line, lowercase, for example
  `fix: reject tampered ciphertext during decryption`.
- No empty commits and no commits that only bump a number.
- Commits use only your configured Git identity. Do not add co-author or
  attribution trailers.

## Code of conduct

Be respectful and constructive. This is a learning and demonstration codebase
and a place where people should feel safe to ask questions and propose ideas.
Harassment or abusive behavior will not be tolerated.
